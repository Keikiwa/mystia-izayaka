# AI Agent 复刻《东方夜雀食堂》夜间经营｜内聚 & 耦合约束提示词规约
> 定位：给你的开发Agent（编码Agent、策划Agent、测试Agent）使用；对齐前面软件工程内聚/耦合知识，适配**经营模拟、状态驱动、多NPC交互、时序经营**的业务特点，不是通用模板；同时适配后续你可能上ECS/整洁架构重构。
> 核心基调：**优先高内聚、可控耦合；允许合理的通信/顺序内聚；红线禁止偶然内聚、内容耦合、公共耦合；耦合只允许最小必要的接口耦合**

> 前置共识（Agent必须先读）
> 业务域：夜雀食堂【夜间经营闭环】：来客→接单→备菜→烹饪→上菜→结算→评价→清台，附带：库存、食材采购、NPC好感、菜谱解锁、环境buff、营业时间、事件分支。
> 不覆盖白天探索、主线剧情等无关模块，保持当前经营子域收敛。

## 【第一部分：全局顶层约束（Agent启动必加载，硬规则，不可自行放宽）】
```
【全局架构前提】
当前目标子系统：东方夜雀食堂 - 夜间经营子系统
架构风格：Clean Architecture + ECS 混合；领域优先；状态与行为分离
内聚等级偏好排序（优先）：功能内聚 > 顺序内聚 > 通信内聚 > 逻辑内聚
❌ 严格禁止：偶然内聚（红线，一旦出现必须立刻重构）
耦合允许白名单：仅【接口耦合(简单数据/值对象)】
❌ 严格禁止：内容耦合、公共耦合、外部耦合（全局裸变量跨模块读写是重大违规）

【内聚取舍总原则（Agent做设计权衡时必须遵守）】
1. 领域业务行为模块（接单、烹饪、结算、NPC评价、好感变更）：强制目标【功能内聚】
2. 状态仓储/资源容器（库存仓库、菜谱库、NPC状态池、餐桌状态池）：允许【通信内聚】，但仓库只封装读写，不夹带业务流程逻辑
3. 固定数据流管线（上菜流程、订单处理流水线、结算校验流水线）：允许【顺序内聚】，管线只编排数据流，不嵌入额外业务规则
4. 纯工具工具包（数值计算、随机roll、时间格式化、图标映射）：允许【逻辑内聚】；工具包禁止混入经营业务逻辑，禁止无限膨胀
5. 批量启动/生命周期编排模块（营业开始、打烊收尾）：允许【时间内聚】，编排逻辑保持极薄，业务逻辑下沉到独立功能模块
6. 任何模块，只要不属于上面四类，不得主动选择低等级内聚；不允许“图省事把无关逻辑堆在一起”

【耦合取舍总原则】
1. 模块之间只传递**不可变值对象、DTO、ID引用**，禁止直接传递内部实体、组件句柄
2. 跨模块依赖只能依赖抽象接口，禁止硬编码依赖具体实现（依赖倒置）
3. 扇出控制：单一业务模块对外依赖接口 ≤4个；超过必须提交架构评审说明理由
4. 禁止跨模块直接读写对方内部私有状态；所有状态变更，必须通过模块对外暴露的接口
```

## 【第二部分：分模块内聚约束细则（给Agent做模块拆分、职责定义时直接对照）】
> 你可以直接丢给编码Agent：拆分模块前，先对照本条判定该模块允许的内聚等级、职责边界、禁止混入内容

### 1. 领域业务模块（目标：功能内聚）
适用模块示例：
`OrderAcceptService` 接单服务、`CookDishService` 烹饪服务、`ServeDishService`上菜服务、`SettleBillService`结算服务、`GuestEvaluateService`客人评价服务、`FavorChangeService`好感变更服务

✅ 内聚要求：
模块内所有函数、逻辑分支，**只为完成一个单一完整经营动作服务**；一句话可以完整描述模块目标；不存在两个独立变更理由（SRP）。
✅ 合法输入输出：订单ID、餐桌ID、客人实体ID、菜谱ID、时间戳、值对象
❌ 禁止混入：
库存直接修改逻辑、渲染绘制、音效播放、存档读写、其他无关业务（例如：接单模块里不能写NPC好感计算）

> Agent自检提问（每次写完该类模块强制自问）：
> 如果我修改【客人拒绝接单的规则】，这个模块是否只有这一处需要改动？会不会顺带要修改上菜、结算逻辑？

### 2. 状态仓储/资源仓库模块（允许：通信内聚）
适用模块示例：
`IngredientRepository`食材库存仓库、`RecipeRepository`菜谱仓库、`TableRepository`餐桌状态池、`GuestStateRepository`客人状态仓库

✅ 内聚要求：
内部多个接口（增、查、扣、重置）共享同一份私有状态；调用顺序无强制依赖；仓库只做状态持久化与校验，**不包含业务决策逻辑**
✅ 合法能力：查询库存、扣减食材、锁定餐桌、读取NPC好感
❌ 禁止混入：
判断能不能做菜、自动结算、客人AI行为；仓库只回答“数据是什么”，不回答“应该做什么”

### 3. 流程流水线编排模块（允许：顺序内聚）
适用模块示例：
`GuestOrderPipeline`客人订单处理流水线、`DishMakePipeline`菜品制作流水线

✅ 内聚要求：
数据流串行：上一步输出作为下一步输入；流水线只串联步骤，业务规则下沉到各个独立功能服务；流水线本身没有独立业务规则
❌ 禁止：在流水线内部写新的业务判断、硬编码分支；流水线只是胶水

### 4. 通用工具包（允许：逻辑内聚，强边界）
适用模块示例：
`ShopMathUtil`经营数值工具（价格计算、好感增量衰减、随机事件roll）、`TimeUtil`营业时间工具

✅ 内聚要求：
内部函数仅属于同一个抽象大类（数值工具/时间工具），互相独立，按参数选择调用；**严禁持续追加无关工具**
❌ 禁止：往MathUtil里面写播放客人音效、保存餐桌状态、生成订单等业务代码（一旦混入，降级为偶然内聚，违规）

### 5. 营业生命周期编排（允许：时间内聚，薄壳）
适用模块示例：
`BusinessBootstrap`营业启动、`BusinessCloseHook`打烊收尾
✅ 内聚要求：
仅仅是同一时刻批量调用多个独立服务，模块本身没有业务逻辑；所有真实逻辑在被调用的功能模块中
❌ 禁止：在启动钩子里面嵌入烹饪规则、好感逻辑

## 【第三部分：耦合约束细则（Agent编码、接口设计、依赖引用强制检查清单）】
```
【耦合白名单：仅允许接口耦合（最小耦合）】
定义：通过公开接口传入纯数据/ID/值对象，调用方不知道被调用方内部实现、内部数据结构

【耦合黑名单，无条件禁止】
1. 内容耦合：模块A直接读取/修改模块B内部局部变量、私有字段、内部函数
2. 公共耦合：多个模块无封装，直接读写同一个全局裸全局变量（例如全局g_inventory、g_favor）；状态必须收拢到Repository仓库，走接口访问
3. 外部耦合：硬编码依赖外部全局信号、全局事件裸总线；事件必须走带契约的消息DTO

【事件通信额外约束（夜雀食堂大量客人AI、时序事件很容易踩耦合坑）】
- 事件消息是只读值对象，不携带实体句柄
- 发布者不知道订阅者是谁；订阅者只依赖消息结构，不依赖发布者模块
- 禁止在回调里直接跨模块修改其他模块状态，回调只调用目标模块的公开接口

【ECS组件/系统额外耦合约束（适配你的技术栈）】
1. Component：纯数据，无行为；组件之间禁止互相引用
2. System：目标功能内聚；一个System只处理一类业务行为；System只能读取/查询它需要的Component集合
3. System之间禁止直接调用；跨System协作优先用事件消息或者上层Application Service编排
```

## 【第四部分：Agent自动自检提示词（写完模块后自动执行，半量化校验，对应前面LCOM等指标）】
> 可以给Agent：写完代码自动跑这套自检，输出自检报告，不通过必须重构
```
==== 内聚自检脚本（Agent执行）====
1. 一句话描述该模块的职责，是否通顺完整？一句话说不完 → 内聚告警
2. 统计模块内的独立变更理由数量：≥2个无关变更理由 → 内聚不足告警
3. 检查是否存在完全无关、游离的函数/分支，不属于本模块目标 → 偶然内聚，阻断
4. 判断当前模块类型，核对它使用的内聚等级是否在允许列表内；越级使用低内聚必须说明理由

==== 耦合自检脚本（Agent执行）====
1. 列出本模块所有外部依赖，统计扇出数量，>4条 → 耦合告警，需要评审
2. 检查所有跨模块访问：是否全部走公开接口，有没有直接访问私有成员/全局裸变量？找到1处即阻断
3. 检查传入参数：是否传递实体句柄、内部组件引用？优先替换为ID+值对象
4. 检查事件回调：回调内部是否直接修改外部模块状态？违规阻断

==== 阈值告警（仅预警，不强制阻断，人工复核）====
- 单模块代码行数 > 450行：预警，检查职责是否溢出
- LCOM指标 > 6：预警，人工复核业务语义（不直接判定错误，防止误杀无状态功能服务）
```

## 【第五部分：违规分级与处理策略（给Agent的SOP）】
1. 🔴 阻断级（红线，必须立刻重构，不允许提交）
   - 偶然内聚
   - 内容耦合、公共耦合（裸全局变量跨模块读写）
2. 🟡 告警级（必须写注释说明权衡理由，等待人工评审，不评审不能合并）
   - 业务模块主动选用顺序/通信内聚而不是功能内聚
   - 模块扇出>4、模块行数超限、LCOM高
3. 🟢 合规级：满足上面内聚、耦合规则，自检全部通过

## 【第六部分：可直接复制给Agent的完整一次性Prompt（你复制丢给开发Agent即可）】
```
你现在负责复刻东方夜雀食堂【夜间经营子系统】的代码设计与实现，严格遵守下面的内聚耦合架构约束，任何设计、编码、模块拆分前先阅读约束：

【业务域边界】仅实现夜间经营闭环：来客、接单、备菜、烹饪、上菜、结算、客人评价、好感变动、库存校验、餐桌管理、营业启停；不混入白天探索、主线剧情。
【架构底座】Clean Architecture + ECS混合；领域行为优先功能内聚。

# 内聚硬性约束
1. 领域业务服务（接单、烹饪、上菜、结算、评价、好感变更）：强制目标【功能内聚】，单一变更理由，一句话说清职责；禁止塞入无关逻辑。
2. 库存、菜谱、餐桌、客人状态这类仓储模块：允许【通信内聚】；仓库只做状态读写校验，不能写业务判断。
3. 订单/菜品流水线编排模块：允许【顺序内聚】；只串联数据流，业务规则下沉到独立服务。
4. 纯数值、时间工具包：允许【逻辑内聚】，严格禁止混入经营业务代码。
5. 营业启动/打烊钩子：允许【时间内聚】，保持极薄，不嵌入业务规则。
6. ❌ 红线：绝对禁止偶然内聚，无关代码不能堆在同一个模块。

# 耦合硬性约束
1. 模块之间只允许【接口耦合】，传递ID、只读值对象/DTO，禁止传递实体、组件内部句柄。
2. ❌ 红线：禁止内容耦合、公共耦合（禁止裸全局变量跨模块读写，所有状态走仓库接口）。
3. 单一业务模块对外依赖扇出上限4个，超过必须提交评审说明。
4. ECS规则：Component纯数据；一个System只做一类行为；System之间不直接调用，使用事件或者上层服务编排。
5. 事件消息只能是只读数据DTO，回调内部禁止直接篡改其他模块状态。

# 写完每个模块，自动执行自检并输出自检报告
自检清单：一句话职责描述、变更理由数量、内聚等级匹配检查、依赖扇出统计、是否存在私有跨模块访问、行数预警。
违规分级：红色阻断级必须立刻重构；黄色告警级必须附带权衡说明，等待人工审核。
不要为了编码省事主动选择更低等级的内聚，只有在架构收益明确、耦合代价更低的时候，才可以选择允许范围内的低一级内聚，并且写清楚权衡原因。
```

## 补充：适配你痛点的小备注
你之前提到：**高内聚的难点是权衡，耦合更容易识别**
这份提示词的设计思路就是：
- 耦合：大量**硬红线、可自动化检查**，Agent可以自己抓错
- 内聚：给Agent划定【哪些场景允许哪一档内聚】，同时强制要求**写权衡理由**，把“纯主观设计选择”变成可评审的显性决策，避免AI图省事直接堆成上帝类、偶然内聚。
